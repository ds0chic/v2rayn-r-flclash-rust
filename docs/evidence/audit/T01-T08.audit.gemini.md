## 结论摘要：有条件通过（存在 5 项 P0/P1 结构性缺陷与反证，必须在进入 T09+ 前整改）

截至 `2fbe9f1`，整个重构项目完成了核心架构的骨架搭建与关键回路接入：
- **反造假方面**：T03 证实确实拉起了外部真实的 `xray.exe` 二进制，使用 Named Pipe 与 Job Object，无内嵌 Mock 伪造内核；端口遵守规矩避开 `10808`；T04 确实使用了真实的 SQLite (rusqlite) 驱动并实现了表结构及迁移逻辑；Config Codegen 完成了庞大的协议生成与差异处理。
- **但审计发现严重的结构性风险与文档夸大/失真**：
  1. **自闭环/自捏假数据**：T04 的合成夹具由被测自身的 `schema.rs` 反向生成，从未引入上游真实的 `guiNDB.db` 二进制进行验证；且导入指纹绑定绝对路径，同一库迁移到不同路径将导致数据全量重复追加翻倍。

  4. **UI 契约断裂与双源混淆**：Dart 状态栏存在死字段与活状态混用的情况；Rust 发出的 `desired_revision` / `applied_runtime_revision` 在 Dart UI 侧完全不显示，`epoch/seq` 被直接丢弃，无断线重连保障机制。
  5. **文档引用大面积陈旧漂移**：T01/T02/T05 的证据文档在合并 T03 之后均发生行号错位、引用不存在的测试文件（`profiles_widget_test.dart`）或包含已被 HEAD 改动推翻的声明。

## 会拖垮后续阶段（T09–T20）的前 5 个结构性问题及最小修复建议

### 1. 结构性问题 1：生成器无 10808 端口绝对禁令（威胁后续联调安全）
- **风险**：后续 T10/T11 界面启动默认入站配置时，上游默认配置正是 10808。如果装配层或用户配置原样流入生成器，将直接写入 10808，侵入用户实际运行环境，引发系统代理抢占与故障。
- **最小修复**：在 `crates/config_codegen/src/xray/mod.rs` 与 `singbox/mod.rs` 的 `validate()` 函数中增加强校验：凡 `local_port == 10808` 或 `state_port == 10808`，立即报错拒绝生成；生成层禁止硬编码 10808 作为兜底。

### 2. 结构性问题 2：T04 导入缺乏真库对照且指纹绑定路径（威胁数据迁移可靠性）
- **风险**：T16 进行实际用户数据导入时，真实用户的 `guiNDB.db` 包含各类变体字段和上游特定的 SQLite 字段格式（如 `VARCHAR`、空值表示等），T04 自捏的夹具无法保证真实兼容性；且由于指纹绑定路径，跨盘迁移或重装后重新导入将导致用户节点列表成倍重复增长。
- **最小修复**：从冻结源码提取一个真实生成的最小 `guiNDB.db` 放入 `fixtures/source`，剥离指纹中的绝对路径哈希，改用 `(content_hash, node_unique_key)` 作为去重基准。

### 3. 结构性问题 3：Revision 机制“后端实现、前端丢弃”（威胁并发与状态一致性）
- **风险**：T09 之后大量并发操作（测试延迟、切换节点、订阅更新、自动故障转移）会频繁下发 runtime 配置。前端如果既不展示 `desired/applied revision`，又在事件层丢弃 `epoch/seq`，将无法发现配置下发未生效（stale revision）或事件丢失，导致界面显示的节点与实际内核跑的节点不一致。
- **最小修复**：在 `apps/desktop/lib/features/runtime/runtime_controller.dart` 中保存并核对 `last_epoch` 与 `last_seq`；在 `status_bar_view.dart` 增加 Revision 的微型状态显示（如 `rev: 3/3`）。

### 4. 结构性问题 4：路由规则条件静默丢失（威胁分流规则正确性）
- **风险**：Xray 路由配置中 `protocol` 条件被静默丢失。当用户导入带有 BT 下载拦截、特定协议阻断规则时，这些规则将变成全协议匹配或条件失效，造成流量意外泄漏（例如 BT 流量走代理导致封号）。
- **最小修复**：修复 `crates/config_codegen/src/xray/routing.rs`，在生成 rule json 时正确追加 `"protocol": json!(rule.protocol)`。

### 5. 结构性问题 5：内核 Job Object 绑定静默容错（威胁系统稳定性）
- **风险**：在 `services/net_host/src/session.rs` 中，`job.assign` 失败只记录了一行 `eprintln`。在 Windows 权限受限或防病毒软件拦截 Handle 复制的场景下，Job 绑定会静默失效。一旦前端崩溃或 net_host 被强杀，`xray.exe` 进程将变成孤儿继续在后台占用端口和网络，导致后续重启失败。
- **最小修复**：若 `job.assign(handle)` 返回错误，强制中止内核启动，直接返回 `E_JOB_ASSIGN_FAILED`，并立即调用 `child.kill()`。

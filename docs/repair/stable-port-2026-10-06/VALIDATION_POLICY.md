# 检查频率与范围（2026-10-07 修订）

本文件统一解释本方案中“门禁”的执行频率。**禁止每完成一张卡/一个字段/一次小改动，就运行全部约290个测试文件、整个Rust workspace、完整release构建和全平台验收。** AGENTS列的是发布门禁，完整检查集中在候选发布；功能覆盖和已知失败合同保留，减少重复执行。

本轮仅调整文档，不运行产品门禁、不改生产代码。已有任务状态、证据和正在进行的改动保留。

## 1. 单任务：定向检查

默认执行层次，不调用不带filter/skip的 `tools/gates/run_all.ps1`。

- 文档/矩阵改动：只检查实际改动的ID、依赖、链接和格式。无需Rust/Flutter门禁。
- 字号、间距等低影响UI调整：改动Dart文件格式、相关静态检查和对应实际界面场景；不为每次样式调整新建镜像测试，不运行全部测试文件。
- 业务缺陷：覆盖本次正确失败合同、相关正常/取消/重试流程和直接关联旧回归。已有覆盖就复用，不要求每卡都新建一个sp_xx测试文件。
- Rust变更：运行确实受影响的package或测试target；涉及public API加直接调用方编译/合同检查。格式与clippy按相关package做，不默认workspace全部。
- Dart变更：格式检查实际文件；需要时 `flutter analyze`（该检查是应用级静态检查，并不等于全部动态测试），只运行相关测试文件/目录。纯Rust任务不默认加Flutter动态测试。
- 修改FRB/IPC、持久化、core/平台链路：补对应真实接口/文件/消费者用例。涉及native runner/engine、AOT或真实DLL接线时才构建相应当前release候选用于场景验证；多个相关卡可共享一个整合候选，不每次保存代码都重建。

示例：SP-05当前实现可针对 `cargo test -p application --locked --test sp05_applied_target` 和 `flutter test test/repair/sp_05_target_contract_test.dart`，再补实际受影响的domain/host调用方检查。它们只是定向示例，不自动宣布该卡全部通过；筛选命中零测试不算成功。

每次证据列明“本次范围/实际结果/未运行范围”。未运行全量不是本卡故障，不为了把所有检查写pass而全量刷一遍；单项implemented/verified仍按真正功能证据评估。

## 2. 跨模块整合：检查受影响链路

触发：共享DTO/FRB/IPC、数据库迁移、public domain/application API、依赖锁或跨层实际运行链发生变化；或多个相关卡完成后准备整合。纯文档/独立间距变化不触发。

整合者汇总一次受影响package/调用方/Flutter测试组，而非每个子任务各跑同一套。例如runtime队列/target/exit合并后，统一跑运行链合同和一次实际核心启动→切换→退出→重试。保存/窗口/路由合并后，统一跑save→apply失败→reconcile→重开。

FRB生成及二次no-diff仅在桥声明、codegen配置、依赖或生成物变更时执行，由一名整合者负责。迁移/restore变更查对应真实SQLite和journal恢复；helper变更查归属/清理合同；代码生成变更测涉及的核心/协议。波及范围不清楚时扩大到相关package/功能域，不能反过来只选最容易通过的用例。

依赖升级/公共底层结构变化可能影响整个workspace，此时整合检查可扩大为全量，但需注明触发原因。阶段整合不是固定“每5张卡全量一次”的机械计数。

## 3. 发布候选：完整门禁

准备交付一个可下载、可实际验收的候选版本时，固定commit/锁文件/工具链，统一跑一次AGENTS完整Rust与Flutter门禁、release构建、当前正式包普通入口和包身份检查。不能将定向结果冒称完整发布门禁。

第一次全量发现失败时：先定位并定向修复/复测，不每试一个修复就重新扫全部文件。修复批次稳定并准备新候选后，再做完整门禁；完整结果只能覆盖其确切源码/依赖/构建版本。不得复用旧版本的完整pass给已改变的最终包盖章。

`tools/gates/run_all.ps1`是现有完整检查/诊断入口，默认会逐Flutter文件启动进程，适用于完整结果收集，不是每卡完成钩子。其现有 `-FlutterFilter`、`-SkipStatic`、`-SkipCargo` 能做定向诊断；带filter/skip的结果必须标“局部”，即使exit0也不叫完整通过。本次不修改或运行该脚本。

稳定的全量batch可统一收集；发生测试进程异常时，重跑受影响文件并记录未完成，不删测试/改skip装绿。要变更具体执行器的批跑/隔离策略，由SP-29独立完成证据和改动，不能在本次文档频率调整中覆盖正在开发的脚本。

## 4. 高成本验收：按影响和交付范围安排

- 14核心：修改某核配置或adapter时，先复验该核及共享能力所影响的核；不因改一个文本标签就重跑14核真实会话。完整移植交付保留适用矩阵，每项证据有明确版本和适用范围。
- 六平台：Windows局部修复不要求立即构建其它五单元；公共依赖/平台共享代码变化影响哪些单元，就补哪些。单平台交付声明真实范围，全平台完整宣称仍需所有适用单元证据。
- 性能：性能路径、渲染、数据查询、依赖或关键运行架构变化时测相关场景；普通文案不重跑全部采样。候选整体需要当前可用性/响应检查。
- 24h/500切换：运行生命周期、资源归属/清理、背压或关键依赖稳定后安排持续验收；不是每卡流程。相关实现未变可引用有环境/版本/代码范围说明的旧证据，受影响时补验，不能借此宣称整个新包自动继承所有稳定性结果。
- OS副作用：仅授权隔离环境对应流程验证，不在宿主为“凑全量”修改代理、路由、DNS、自启；10808和进程归属边界不变。

降低的是检查频率与重复范围，不删已知失败、不降低完成要求，也不新加按测试数量计算的完成百分比。后续执行模型必须先读本文件，再读卡中具体行为断言；历史命令日志保持原样，旧“每卡全workspace”的模板要求由本频率规则替代。

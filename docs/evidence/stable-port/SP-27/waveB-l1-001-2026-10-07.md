## 5. Gaps (registered, not privately fixed)

1. **Bridge apply routing (exact):**
   `crates/bridge_api/src/api/t16.rs::t16_apply_core_update` (~lines 946-957)
   requires `(asset_name, download_url, remote_version)` all `Some` and skips
   otherwise. Geo rows carry `None` for all three by design (no version, apply
   recomputes URLs), so selecting `GeoFiles` in apply is an honest
   `skipped: ["GeoFiles"]` today. Driving geo apply from the update window
   needs a bridge change routing `core == "GeoFiles"` to
   `UpdateService::apply_geo_files` (and optionally surfacing per-file
   hashes). No DTO/FRB change is required: `CoreUpdateDto`/`UpdateReportDto`
   already carry the row as-is. Not made (bridge_api frozen for this card).
2. **Settings→service wiring:** `UpdateService::geo_source` defaults to the
   upstream built-in; the settings layer must call `with_geo_source(
   dns::effective_geo_source(&const_item))` so a stored `GeoSourceUrl`
   (incl. RU/IR presets) reaches the update flow. Engine resource pass reads
   the settings tree directly and is unaffected.
3. **Scope kept out:** `OtherGeoUrls` extras (`geoip-only-cn-private.dat`,
   `Country.mmdb`, `geoip.metadb`) and routing-derived SRS rows are served by
   the engine periodic pass (`build_resource_requests`), not the update row.
4. **External/real-source items (remain):** controlled real-source download
   (pinned geo origin + hash manifest), real product key/package/isolated-OS
   acceptance — real remote stays unverified by task scope.

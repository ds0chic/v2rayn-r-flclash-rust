### 1.1 幂等性

脚本连续执行两次均 exit 0，产物被覆盖重建（后续运行由 `-SkipBuild -SkipFlutter`
复用已编译产物，或全量重建）。两次 zip 的 SHA-256 **不同**
（第一次 `4c88ed…`，重建后 `cf729e…`），原因是 `Compress-Archive` 在 zip 内
写入文件时间戳。**因此以成员内容清单哈希作为可复现性度量**。

## 2. 干净环境冒烟（真实执行）

脚本：`tools/release/smoke_windows.ps1`（启动/窗口/数据/钩子/清理）与
`tools/release/capture_apply_evidence.ps1`（真实 apply 运行态截图）。

- 解压到独立临时目录（如
  `%TEMP%\t20_smoke_<guid>\extract\v2rayN-R-1.0.0+1-windows-x64\`）；

- 不触碰 10808、系统代理、TUN；只杀本脚本启动的 PID 及其后代。

### 2.1 结果

| 运行 | 窗口出现 | 截图 | 数据文件 | 退出清理 |
|---|---|---|---|---|
| update（`V2RAYN_R_OPEN_UPDATE=1`） | ✅ | `T20-smoke-update-window.png` (1200×800) | 首运行落 `guiNDB.db`（+wal/shm）；`guiNConfig.json` 惰性写入 | ✅ CloseMainWindow 后退出 |

`T20-smoke-summary.json` 中 `seed_apply.applied=false` 是**探测节流导致的记录偏差**
（1s 间隔在进程拆除后才检查；该脚本已改为 300ms）。真实 apply 结论以
`capture_apply_evidence.ps1` 的独立运行为准（§2.2），两者日志均在 `T20.runs/` 保留。

- **窗口出现**：两张窗口截图为本机真实截屏，可见 `检查更新` 与

- **数据目录**：首运行生成 `guiNNDB.db`（4 KB + `-wal`/`-shm`）；
  `guiNConfig.json` 仅在发生设置保存/种子写入时落盘（默认首启动未保存设置，
  属惰性写入，非缺陷）。种子运行确认 `guiNConfig.json` 正常写出（`Inbound[0].LocalPort=11808`、
  `active_index_id=t18b-node`、`desired_revision=2`）。
- **退出清理**：`CloseMainWindow` 后进程退出；端到端探测
  `state=running compressed=True`（apply 后端口释放）。

### 2.2 真实 apply 链（打包产物，决定性证据）

方式：用既有 `crates/bridge_api/examples/t18b_seed.rs` 在**全新数据目录**播种
合成 VLESS 节点（`192.0.2.10:443`，`active`，inbound `11808`），再以
`V2RAYN_R_AUTO_SMOKE=1` + `V2RAYN_R_XRAY_BIN` + 打包的 `net_host.exe` 启动。

观测（`docs/evidence/T20.runs/apply_evidence.log` 与
`docs/evidence/T20.screenshots/T20-applied-artifacts/`）：

- net_host 写出 `config.json`，内容为真实 mixed 入站 127.0.0.1:11808 +
  VLESS 出站（192.0.2.10:443）+ DNS + routing（见 artifact 原文）；
- 打包的 Xray 读取该配置并启动（`core.log`：
  `Reading config: ...\config.json` → `Xray 26.3.27 started`）；
- 就绪探测通过，11808 监听，journal `stage=applied`
  （`pid=41560`、`config_sha256=3c168c4d…`、`port=11808`、`rev=2`）。
- 运行态截图：`T20-smoke-applied-running.png`。

> 说明：一次早期冒烟因探测间隔过大（1s）在进程拆除后才检查，只看到
> `applied=false`；改用 ~300ms 间隔重测后捕获到 Running 状态。先前日志页出现的
> “Xray 找不到 config.json”属于 rollback/拆除后重试读取的时序结果，非配置生成
> 缺陷。两次结果均在 `T20.runs/` 保留，供复核。

### 2.3 开发路径依赖检查（方法学限制，如实登记）

- **未使用 Process Monitor**，未做系统级路径追踪，故**不能证明“无开发路径依赖”**。
- 依据：打包产物在独立临时目录、`V2RAYN_R_DATA_DIR` 指向临时目录、不设任何
  `V2RAYN_R_*` 核心路径变量时，进程启动、窗口、数据生成、退出均正常；`net_host`
  由同包目录定位（`net_host_client.rs` 同级查找），未回退到 `target\debug|release`。
- 残余风险：DLL 搜索路径、CRT 版本等未逐项追踪。登记为未证明项。

## 3. Windows ARM64 尝试

命令（`apps/desktop`）：

```powershell
flutter build windows --release --target-platform=windows-arm64
```

结果（原文）：

```
Could not find an option named "--target-platform".
Run 'flutter -h' (or 'flutter <command> -h') for available flutter commands and options.
exit 64
```

`flutter build windows --help` 中无任何架构/`--target-platform` 选项；pinned
Flutter 3.47.5 的 Windows 桌面构建不提供架构选择。结论：**当前 CLI 不支持
直接产出 Windows ARM64**（需 ARM64 主机与相应引擎/工具链，本环境未具备）。
已写入 `compat/platform-matrix.md` §6（状态 `blocked`）。
